# Upgrade 1.8 to FabrCore 2.0.0 GA

Contents: packages; runtime/configuration; ACL migration; persisted state/Orleans;
compaction; operational behavior; verification.

## Packages and code

Use .NET 10, align direct Orleans references to 10.3.1 and Agent Framework to 1.20.0,
and pin supported FabrCore package references to 2.0.0.

| Remove retired reference | 2.0 owner |
| --- | --- |
| `FabrCore.Services.Contracts` | `FabrCore.Core` |
| `FabrCore.Services.Memory` | Implementation in `FabrCore.Host`; contracts in Core; remote clients and harness integration in SDK |
| `FabrCore.Services.GraphRag` | Implementation in `FabrCore.Host`; shared contracts in Core |
| `FabrCore.Host.SqlServer` | `FabrCore.Host` |

There are no forwarding packages. Update both NuGet and project references, central package
entries, build/publish lists, and consumer libraries; rebuild all affected assemblies.
Preserved `FabrCore.Services.Memory.*` and `FabrCore.Services.GraphRag.*` namespaces do not mean
the old packages still exist. Check assembly-qualified type names and reflection-based loading.
The old lightweight `FabrCore.Sdk.Memory` API is removed; migrate its storage/tool integration
explicitly to the scoped Memory service instead of only changing a using directive.

Host, Core, SDK, Surface, Client.Orleans, Client.WebSocket, Host.AzureStorage, Host.Testing,
and Services.Microsoft365Copilot are the nine supported packages. Agent libraries can depend
on SDK/Core without taking a SQL implementation dependency.

Remove manual `AddAgentMemoryServices`, `AddMemoryAdministration`, `AddGraphRagServices`, and
`AddGraphRagAdministration` calls from normal Host startup. `builder.AddFabrCoreServer()` now
registers integrated services according to database mode. Preserve application-specific options
through the supported options/configuration path rather than deleting their intent.

## Choose runtime and configuration

Without a feature connection, the default is a trusted standalone workspace: cross-principal
agent messaging does not require ACL grants; SQL-only features and ACL administration are
unavailable. Authentication, privileged admin authentication, and storage/session ownership
checks still apply. Default runtime state, conversations, typed storage, delivery checkpoints,
and reminders are in memory and disappear on restart.

To retain enforced ACL and enable integrated SQL persistence, Memory, GraphRAG, and operational
stores, configure a pre-existing SQL Server 2025/Azure SQL database supporting the vector/graph
schemas. Supply the secret via `ConnectionStrings__FabrCore` or the equivalent secret provider.
Minimal application configuration shape (replace the connection value through secrets):

```json
{
  "ConnectionStrings": { "FabrCore": "<SQL connection from secret source>" },
  "FabrCore": { "Database": { "AutoInitialize": true } }
}
```

`FabrCore:Database:ConnectionStringName` defaults to `FabrCore`. Optional
`MemoryConnectionStringName`, `GraphRagConnectionStringName`, `AclConnectionStringName`, and
`OperationsConnectionStringName` select existing split databases. These require the main
feature connection. Preserve old Memory/GraphRAG database mappings to retain existing data.

Configure `default` chat and `embeddings` models and credential aliases in the active model
store; GraphRAG requires 1536-dimensional embeddings. Extraction resolves an explicit override,
then `graphrag`, then `default`. SQL startup validates settings without paid inference.
Memory remains a per-agent plugin/scope choice; SQL mode does not attach it to every agent.

The standard local `fabrcore.json` supplies `ModelConfigurations` and `ApiKeys`.
Put runtime settings under `FabrCore` in appsettings (connection strings stay at their normal
top-level .NET location). GraphRAG ingestion tuning remains a legacy exception under top-level
`GraphRag:Ingestion`; the extraction alias uses `FabrCore:GraphRag:ExtractionModelName`, and
Memory tuning binds from `FabrCore:Memory`. Do not invent `Database:Enabled`: mode is resolved from the connection.

Startup initializes required tables and GraphRAG migrations. With `AutoInitialize=false`,
pre-provision schemas and migrations; startup validates them. Invalid connections, missing models,
or schema failures fail startup rather than falling back to standalone. Mode changes need restart.

Explicit Azure/custom Orleans providers remain supported. Preserve cluster/service IDs, storage
provider names, and existing Orleans connection overrides. Orleans storage selection alone does
not enable SQL knowledge/ACL features, and an explicit `ClusteringMode: Localhost` overrides the
SQL Orleans default even when the feature connection exists. Review that setting deliberately.

## Migrate ACL before cutover

ACL entities/version move from Orleans state to relational `acl` tables. Normal startup rejects
`FabrCore:Acl:Seed`, legacy `Acl:Seed`, and `FabrCore:Acl:Rules`. Maintain principals, groups,
roles, membership, and grants through the protected admin API after migration.

The following paths are relative to this skill folder. The utility reads the credential from
`FABRCORE_ADMIN_API_KEY`; supply the appropriate old/new host credential through the environment.

1. Back up old databases and retain binaries/configuration. While the old host is available,
   export to a new file:
   `./scripts/Migrate-Acl.ps1 -Mode Export -HostUrl https://old-host -Path acl-export.json`
2. Configure the new SQL host and `FabrCore:AdminAuthentication:ApiKey`. Remove startup seeds/rules
   after preserving them as migration input. Initialize schemas on the migration target.
3. Import into a target containing only built-in ACL entities:
   `./scripts/Migrate-Acl.ps1 -Mode Import -HostUrl https://new-host -Path acl-export.json`
4. Check identities, memberships, preserved grant IDs, allow/deny behavior, and readiness before
   routing application traffic to the new host.

Import validates references, preserves IDs, and commits transactionally. It refuses to overwrite
user-defined target ACL data; do not clear that data to force the import. An old JSON document
containing `FabrCore:Acl:Seed` is accepted as migration input. Export/import does not migrate
Orleans conversations, application data, or Memory/GraphRAG databases. Freeze ACL writes during
the final export/cutover so later source changes are not omitted.

## Persisted state and Orleans

Restore a copy of existing SQL/Azure state with application-specific payloads before production
cutover. Orleans JSON storage now validates `$type` against the type manifest. For unregistered
application types, configure the silo through the server options callback:

```csharp
options.ConfigureOrleans(silo => silo.Services.Configure<
    Orleans.Serialization.Configuration.TypeManifestOptions>(manifest =>
        manifest.AddAllowedType(typeof(MyPersistedType))));
```

Register nested types as needed; keep `AllowAllTypes` disabled. This does not switch storage
formats. The JsonElement converter preserves JSON on subsequent writes but cannot recover
content already lost in old data. Contract analyzer baselines do not establish compatibility
with every old client: coordinate host/client upgrades and validate any mixed-version rollout.

Memory streams remain the default. Optional `FabrCore:Orleans:SqlServerStreams=AdoNet` uses the
pinned **10.3.1-alpha.1** streaming provider, even though FabrCore 2.0 is GA. Adoption is optional.
All silos must use the same stream mode. Stop publishers/drain work and restart the cluster when
switching; memory queues are not migrated. Direct stream clients call
`client.AddFabrCoreSqlServerStreams(clusteringConnectionString)`; grain-only clients do not need
SQL credentials. Stream queues use the clustering database, not `StorageConnectionString`.
If Orleans `AutoInitDatabase=false`, apply the release's `SQLServer-Streaming.sql` before enabling
SQL streams (`SQLServer-Main.sql` first for new databases). Keep consumers idempotent.

Update telemetry queries: `rpc.system` becomes `rpc.system.name`, `rpc.service` becomes
`orleans.rpc.service`, and `rpc.orleans.target_id`/`source_id` become
`orleans.rpc.target_id`/`source_id`. `rpc.method` includes the interface and method.

## Compaction and harnesses

Both standard SDK-created agents and harnesses compact working context inside the tool loop,
before subsequent model calls. Original tool output stays in persisted history. Configure
`ContextWindowTokens` and `MaxOutputTokens`; optionally set `ContextWorkingSetTokens` or
`_ContextWorkingSetTokens` below the physical input budget. Protected oversized content can
stop a run; thresholds are not guaranteed hard caps.

Remove assumptions that durable compaction defaults to 87% or always uses one model call.
Automatic durable compaction uses 70% of a configured input working set, with a 75% fallback
when absent. Summaries require model metadata, reserve output/headroom, and use bounded
reduction (eight passes, 64 calls). `_CompactionModelConfigName` or
`CompactionConfig.SummaryModelConfigurationName` can select the summarizer.
Validated writes preserve instructions, the latest user message, and latest interaction group;
invalid or stale compaction results leave history intact. Handovers are assistant context.
Memory-aware compaction is separate opt-in behavior.

Harness background waits default to 300 seconds via `_HarnessBackgroundWaitTimeoutSeconds`.
Continue using the result's `RunAsync` for persistence and test mode/snapshot restoration.

## Operational behavior and acceptance checks

SQL mode selects durable audit, evidence, and A2A snapshots in `fabrOps`. Custom providers remain
supported. SQL failures do not activate in-memory fallback. Audit writes log/count failures but
do not spool retries; retention/pruning must be explicit. Evidence signing still needs explicit
configuration; persistence does not enable signing or store private keys.

A2A snapshots survive restart, but SSE streams are not durably replayed. Interrupted execution
fails rather than automatically rerunning effects. Terminal retention defaults to one hour;
configure it for application requirements and test cross-host task reads/cancellation.

Verify restored conversations/custom state; typed storage; delivery retries; ACL isolation;
Memory scope/write/recall behavior; GraphRAG ingestion/search against migrated schemas; admin
credentials; and affected WebSocket/A2A/Copilot clients. Test both startup and a process restart.
Do not enable experimental retrieval/consolidation options just to complete an upgrade.
